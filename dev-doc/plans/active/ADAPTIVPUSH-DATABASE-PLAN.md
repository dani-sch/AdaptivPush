## Common new-data contract

Every new authoritative mutation validates caller identity on the server, expected revision, complete parent lineage, schema/policy version and a stable owner-scoped operation ID. A replay with identical payload returns the original result; the same operation ID with a different payload is rejected. Multi-row finalize/activate/install/accept operations use one database transaction. The client never supplies a trusted moderator role, verified-use marker, purchase validation, final entitlement or public-safe flag.

Use opaque UUID identities, UTC event instants, explicit local calendar date plus IANA schedule timezone for placement, and integer monotonic revision numbers. Do not derive cycle identity from the current wall-clock week. Unique indexes scope replay to `(owner_id, operation_id)` and mutable roots use expected-revision compare-and-swap. Operations may be recorded in domain rows or a narrowly scoped operation-receipt contract; a global event platform/new table is not automatically required. JSON payloads require versioned validation, bounded size and explicit allow-lists; opaque JSON is not an integrity strategy.

Authority classes used below:

- **Private:** authenticated owner reads; writes must check parent ownership and same-instance lineage. Simple preference edits may use RLS CRUD; cross-row operations use commands.
- **Append:** owner reads; validated command inserts, normal client UPDATE/DELETE denied for accepted new-format records. Corrections append superseding references. Account erasure remains possible through the deletion service.
- **Published:** private author drafts plus a sanitized version/projection; immutable publication and visibility resolution use trusted commands. Initial visibility is unlisted; public discovery stays disabled.
- **Service:** no ordinary client writes; minimally privileged server/provider command, owner reads only where appropriate. Verified entitlements are never auth-metadata claims.
- **Moderated:** authoritative audience, block, report and moderation checks on server; confidential reporter/case information is separated from public projections.

Index foreign keys used for ownership and hot queries; review actual explain plans and write cost before adding redundant indexes. Add constraints after a preflight invalid-row report; backfill in restartable bounded batches with watermark/checksum/reject counts. Validate constraints before requiring non-null fields. New sensitive tables deny anonymous access and receive RLS/grants together in the introducing migration, including linked-owner negative tests. Distinguish immutable user records from retention: append semantics do not exempt personal data from erasure.

## Compatibility, deletion and rollback procedure

1. Capture schema/role drift and invalid-row counts without exposing user payloads. Establish tested backup/restore. Review each slice's migration, client minimum version, constraints, security policy and forward-fix path together.
2. Add nullable fields and versioned contracts before required links. Introduce only the tables needed for the slice. Deploy owner/command policies in the same transaction as new sensitive surfaces. Do not deploy permissive defaults for convenience.
3. Ship readers that distinguish legacy/new schemas, missing rows, missing schema, offline, permission denial and malformed data. Maintain a bounded compatibility window with telemetry for old-client writes and fallback use; assign a retirement owner/date after actual adoption evidence, not an invented date in this plan.
4. Backfill only recoverable facts with provenance and source checksums. Unmapped catalog IDs, unknown completeness, unknown original dates and missing rationale remain unknown. Quarantine rejects for review; do not delete them or coerce their meaning.
5. Validate constraints and reader parity before enabling writers. Atomic commands reject stale revisions and wrong-parent references even when all rows have the same owner. Clients cache accepted immutable snapshots and persist outbox operations locally; logout/account switching must isolate and clear sensitive cache according to explicit user-safe recovery rules.
6. On failure, disable the new producer/writer, preserve safe reads and durable pending work, reconcile receipts and forward-fix schema. Do not drop new tables or delete accepted artifacts as routine rollback. Never return to insecure catalog writes, silent readiness escalation, automatic missed-work debt or a false success state.
7. Account deletion is an authenticated, auditable process across database, storage, device cache and third-party/provider state. Private health/readiness/equipment data is removed under disclosed policy; public distribution is disabled and attribution/provenance minimized. Pinned recipients keep the reusable sanitized training artifact where allowed, never the deleted author's personal data. Restricted financial/moderation retention and expressive-content terms require qualified review; this document invents no retention duration or legal basis.
