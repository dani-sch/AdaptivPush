## Register mechanics and universal slice contract

AP identifiers never encode release order or change when work moves. Bounded tasks use `AP-01.1`, etc.; do not re-use an ID for another outcome. Status progresses `QUEUED -> INSPECTION -> IN PROGRESS -> LOCAL VERIFIED -> INTEGRATION VERIFIED -> RELEASED`; use `BLOCKED` with a concrete missing prerequisite. A planning document is not evidence of any later state. Each slice may be delivered as the independently reviewable packets below; shared foundations are added only with their first consumer.

Every slice inherits **G-01 through G-10** and its explicit exceptions below. These are required fields of every execution packet, not optional boilerplate:

| Gate | Entry, execution, and exit requirement |
|---|---|
| G-01 Scope and ownership | Re-read current git state and code status; name the bounded task, owner route, affected contracts, exact files, and dependencies. Preserve unrelated changes; feature branch only. Future paths below are proposed and absent unless code status says otherwise. |
| G-02 Identity and persistence | Check ownership, operation ID, base revision, schema/policy version, immutable accepted prescription, actual-vs-planned distinction, and account isolation. Replayed commands return the original outcome; stale commands require explicit reconciliation. |
| G-03 Data and compatibility | Use the owning database slice design; inventory actual columns/grants first. Add only needed schema, stage backfills with resumable checkpoints, test old/new/missing schema, and retain readable legacy data. A migration file alone is not a deployed schema fact. |
| G-04 Commercial and privacy | Test free/premium/downgraded access; entitlements, consent, rollout flags, and presentation depth are independent. Actual records/history and accepted outputs remain available. Minimize logs; sensitive context stays private; clear account caches on switch/signout. |
| G-05 Offline and errors | Demonstrate cold cached launch, supported local draft/write persistence, restart, retry, expired auth, unavailable service, account switch, and conflicting device revisions. Pending differs from complete, failed, and zero. Never lose entered work to an optional engine or UI refresh. |
| G-06 User interface | Exercise loading, empty, partial, unavailable, pending, conflict, retry, and success states. Verify VoiceOver/TalkBack labels/focus, dynamic type, contrast, non-color status, touch targets, reduced motion/haptics, and light/dark/system with retained palettes. |
| G-07 Smallest local gate | `npm run lint` for application edits plus deterministic tests covering the slice's actual failure boundary. AP-01.2a added the first focused Expo/Windows-compatible TypeScript harness as `npm run test:catalog`; current package scripts also cover dependencies, workouts, programs, availability and database concurrency. Proposed later-slice tests remain absent until implemented. Use `npx tsc --noEmit` for changed contracts. SQL validation and transaction/RLS tests use an authorized isolated environment before deployment. |
| G-08 Integration and release | Reconcile through configured `integrator` or an explicitly approved alternative; do not assume it exists. Verify migration ledger/restore, authenticated multi-user boundaries, old/new clients, and real Expo device UI. Every release additionally consumes relevant AP-16 operational packets. Public features require named moderation/support owners. |
| G-09 Rollout and recovery | Deterministic per-capability flags default off for new behavior; server enforcement for privileged access. Measure errors/conflicts/replay and actual outcome coverage without raw symptoms or health payloads. Disable the producer/write path before destructive rollback; preserve readable accepted artifacts and history. Never revert to known hidden escalation or unsafe write authority. |
| G-10 Evidence and completion | Record base/final commit, schema and policy versions, exact command, environment/date, fixtures/results, limitations, screenshots where relevant, flag/rollback rehearsal, and owner in `dev-doc/reports/DEV-LOG.md`. Attach a slice-specific evidence artifact using `dev-doc/reports/ADAPTIVPUSH-AP-NN-<date>.md` when substantial (planned pattern). Link each relevant AC-TR acceptance row. Do not mark a slice complete with open required gates. |

All acceptance examples below supplement the full `AC-TR-*` rows assigned to that AP slice in the traceability map. Reverse navigation uses that document's AP index. Evidence paths denote future artifacts until linked to an actual result.

## Release graph and safe parallel work

Approved release sequence: authority/provenance -> durable records -> free scheduling/progression -> advanced generation/equipment precision -> contextual coaching -> unlisted publishing -> optional health/cosmetics -> operationally gated public/community. AP-16 is a set of release obligations embedded in those waves, not a final opportunity to postpone privacy or account recovery.

| Wave | Slices | True prerequisites | Sequencing preference or optional enrichment |
|---|---|---|---|
| Trust and durable use | AP-01, AP-02, AP-03 | Catalog command boundary, migration/restore evidence before production data changes; workout/program identity contracts before their durable writes | AP-02 and AP-03 can be built against agreed contracts in parallel; release both before broad new planning behavior |
| Free training | AP-04, AP-05 | Durable occurrence/prescription/session identity and replay protection from AP-02/03 | History/progression selector development can run beside schedule UI; adherence awaits schedule fulfillment |
| Paid convenience | AP-06, AP-07 | AP-03 installer, AP-04 placement, AP-05 performance contracts, AP-16 verified capability access | Generator structure and equipment profile UI can develop separately; exact-load generation waits for AP-07 load contract |
| Coaching | AP-08, AP-09, AP-10 | AP-02 frozen capture, AP-03 revisions; AP-09 comparable history; AP-10 AP-04 schedule revision command plus AP-08 proposal lifecycle | Readiness safety defect containment can occur earlier; advanced generation, wearables, and public publishing are not prerequisites |
| Unlisted distribution | AP-11 | AP-03 private installation; AP-04 placement; AP-16 deletion/support and distribution handling | Does not require premium coaching, health, themes, discovery, or social |
| Optional adapters | AP-12, AP-13 | AP-16 consent/privacy or purchase verification respectively; functioning free core | Health and themes may proceed independently after core gates; neither blocks coaching or unlisted sharing |
| Public operations | AP-14, AP-15 | AP-11 versions; AP-02/04 eligibility for reviews; AP-16 moderation/support capacity | Discovery/reviews before feeds is a release preference; individual social interactions require their own moderation gate |

Critical path for trustworthy free training: `AP-01 -> AP-02 + AP-03 -> AP-04 + AP-05 -> applicable AP-16 release proof`. First monetizable precision adds `AP-06 + AP-07 + AP-16 purchase verification`. Public readiness is not on the core critical path. Parallel teams must avoid concurrent edits to `hooks/useCurrentProgram.ts`, `app/next-workout.tsx`, and shared database types without an explicit integration owner; agree contracts first and separate commits by consumer. These lanes describe future implementation opportunities, not permission to start implementation during consolidation.
