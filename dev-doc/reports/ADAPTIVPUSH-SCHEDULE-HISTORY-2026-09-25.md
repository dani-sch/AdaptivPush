## Integration contract and compatibility boundary

These are release invariants, not a claim that the implementation below already enforces them:

- A schedule occurrence identifies one intended relative `program_days.stable_day_id` within one installed program/cycle. Its original dated placement is immutable once accepted; current placement changes only by an explicit schedule revision. A workout occurrence refers to a real prescription. An empty non-rest legacy day is neither a rest nor a fabricated workout.
- A program prescription revision changes future exercise/set content without changing occurrence or cycle identity. A schedule revision changes accepted placement without rewriting prescription identity. Actual performed sets remain attached to the frozen selected workout/session even after either later revision.
- One finalized session may fulfill at most one occurrence and an occurrence may be fulfilled at most once, in the existing atomic finalization transaction. Correction may change effective outcomes on the same session without creating a second fulfillment. A draft on another offline device is not known to the server; keep it locally, refresh server revision, and expose the conflict before submitting a changed request.
- Never infer the original dates of historical sessions from `programs.start_date`. Existing programs remain trainable before the user confirms a prospective initial placement; new installations need an explicit placement choice before dated Today can take authority. Archive/restore retain checkpoints and original evidence; restarting is a distinct explicit choice.
- A local date belongs to the accepted IANA schedule timezone, not the current device offset or a UTC calendar day. DST changes UTC reminder instants, not program identity. Travel or a reporting-week boundary requires an explicit keep-dates versus future-replace preview; accepted pauses preserve the optional weeks-on-plan count without incrementing it.
- Offline commands retain their exact owner/program/operation ID, versioned serialized request and expected schedule revision until receipt reconciliation. A stale preview may be refreshed/rebased only as a *new* operation after the uncertain old request has been resolved; no automatic date-passage catch-up or rewrite of pending bytes.
